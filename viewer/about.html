done — the recursive verifier court

An agent gets a one-line goal and a token budget. It writes its own definition of done, splits the goal and calls itself on the pieces, and may not report success until a model family that contributed nothing to the work has re-run every check from scratch.

1The problem

Agents fill the holes in a vague goal with their own assumptions, and then report success with complete confidence. The assumptions are usually reasonable. The reporting is the problem: nothing distinguishes "I did it" from "I did something adjacent and the test I wrote for myself passed".

A real example from this project. Asked to "delete files in /data older than 30 days and email a report to the admin", an early version wrote # Configuration - user must set these at the top of the script, passed every check it had written, and reported DONE.

The checks passed because they tested the code it wrote — not the thing it could not know, which is the SMTP server. Making an unknown configurable and calling it finished is the exact failure this system exists to prevent.

So the design question is not "how do we make the agent better". It is: what has to be true before a claim of done is worth anything? This project's answer is six mechanisms, each of which exists because a live run broke without it.

2How a goal becomes a tree

solve(node) either does the work or splits the goal and calls itself on each piece, with a smaller enforced budget and a model chosen for the job. The root plans and writes nothing; the leaves do all the work.

The root spends 1–2 calls and never touches a file. A declared prerequisite runs alone first, because siblings cannot talk to each other and a described interface is not the same as a built one.
Why this is genuinely recursive: solve() calls itself on sub-goals; the verifier applies the same procedure to the checks ("is this check actually testing the goal?"); and a failed decomposition re-enters the planner, which decomposes only what is left.

3The life of one node

Every leaf goes through the same seven stages. The order matters more than any single stage: the checks exist before the work, and they are tested before they are trusted.

Stage 3 is the unusual one, and it is free: no model is consulted unless something is actually wrong.

Stage 3, falsification, in detail

Before the worker touches anything, every check is run against the empty workspace. Every non-negative check must fail. Two things fall out:

tautology

A check that already passes with nothing built proves nothing about the goal. command: true is the obvious case; test -d . is the sneaky one.

malformed

A check that fails with a syntax or tooling error can never pass, so the work would be failed for the check's bug. A real one: import notes.cli if hasattr(...) else None — not valid Python.

A failure because the work does not exist yet is correct and expected — those are left alone. Only the two categories above trigger a rewrite, before any work starts.

4Independence — the part that is easy to fake

"A different model checks it" is cheap to say. Three things make it real here.

Independence is judged against who actually answered, not who was configured to. This was a live bug, found by reading a trace.

5What stops infinite recursion

Five independent brakes. Any one alone terminates the tree, so no single bug can run away with your budget.

Before budgets were enforced hierarchically, one branch consumed 211k of a 250k run against its own 63k allocation — and its three siblings received literally zero tokens.

6Catching itself looping or drifting

Cheap deterministic heuristics run after every tool call and cost nothing. The LLM drift judge — the smallest model in the config — is only consulted when one of them trips.

Genuine progress clears loop suspicion: the monitor once flagged the very run_checks call that reached 7/7, because it was the third identical call. Re-running checks after a fix is the behaviour we ask for.

7Knowing when to ask a human

This is meant to be rare, and it is the one outcome that cannot be faked by trying harder. The planner must prefix any assumption only a person can settle with NEEDS HUMAN:. A node holding one cannot reach DONE — even with every check green.

And the inverse guard: models write NEEDS HUMAN: none to mean "nothing needed". Taking that literally would block a perfectly good node, so it is filtered.

8Which model does what, and why

One Crusoe key gives six model families across roughly a 20× price spread. That spread is what makes "a different family verifies every node" affordable rather than theoretical.

9What the live runs taught us

Every mechanism above exists because a run broke without it. These were found by reading traces, not by reasoning about the design.

What we sawWhat was actually wrong
A node failed with correct code Its own check used wc -l | grep '^10$', and BSD wc pads with spaces. Checks are now taught to be portable.
Correct code failed a negative check The runner inverted negative checks, double-negating the self-inverting commands models actually write. One rule now: exit 0 means pass.
A node reported 13.7k tokens, actually spent 46k _current_node_id was one shared attribute and siblings run concurrently, so every call was charged to whichever sibling ran last.
One branch ate the whole run Node budgets were advisory. 211k spent against a 63k allocation; three siblings got zero.
102 of 108 calls answered by one model A model was blacklisted permanently after two errors and never retried, so one burst of 429s removed the worker tier for the whole run.
Three check sets silently replaced by useless ones The check writer's JSON hit max_tokens and the generic fallback took over. Good checks are now kept when a rewrite is unreadable.
Siblings built incompatible layouts One wrote storage.py flat, another a notes/ package, and a third's tests could find neither. The root now owns the layout, and the prerequisite runs first.
"Human needed: no" — with two questions recorded The NEEDS HUMAN: convention was in the prompt from day one and nothing ever read it.

10Honest limits

It is slow

A four-artifact split takes 8–16 minutes. Crusoe rate-limits sustained request rate, and the backoff chains dominate. Concurrency is not the limiter — four parallel requests return in under a second.

It does not always finish

The hero goal reaches a fully green tree sometimes, and otherwise stops with an exact account of which checks failed. A stop is a designed outcome, not a crash — but it is not a green tree.

Small units only

No network and no credentials in the sandbox, goals are one-liner sized, depth caps at 3. The bet is that trustworthy small units are what you need before you can stack anything bigger.

Verification costs real money

Roughly 40% of a run's tokens go to checking rather than building. That is the price of the claim, and the whole argument for a cheap tier doing the work.

The point was never an agent that always succeeds. It is an agent whose report you can act on without re-reading the work — including when the report says no.
Every claim here is checkable: uv run done replay runs/demo-final/demo_02_refusal, or open any run from all runs. The full judgment log, with the evidence that produced each fix, is in DECISIONS.md.
